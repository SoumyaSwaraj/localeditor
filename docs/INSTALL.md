# Installing LocalEditor: the whole suite, or one studio

Owner request (12 November 2026): "give option to install either the design studio or the pdf studio only or the whole local editor suite when installing the web app."

One site, one offline worker, three installable apps. People pick one in our own install sheet. What the device keeps offline follows that choice.

## The three apps

| App | Manifest | `id` (never change) | Scope | Start page | Home-screen name |
|---|---|---|---|---|---|
| LocalEditor (everything) | `manifest.webmanifest` (unchanged) | `/` | `/` | `/` | LocalEditor |
| LocalEditor Design | `manifest-design.webmanifest` | `/studio/` | `/studio/` | `/studio/?app=design` | LE Design |
| LocalEditor PDF | `manifest-pdf.webmanifest` | `/pdf-studio/` | `/pdf-studio/` | `/pdf-studio/?app=pdf` | LE PDF |

All three are generated by `scripts/build.js` (`manifestJSON`, `appManifestJSON(app)`, `APPS`) and checked by `tests/install.test.js`.

**Names.** `short_name` is what a phone shows under the icon (about 12 characters before it is cut). "LE Design" and "LE PDF" (9 and 6) are never cut, keep the brand next to the shared icon, and sort right next to "LocalEditor" in alphabetical app lists, so the three read as one family. A bare "Design" or "PDF" would collide with system apps and other PDF readers. The full `name` ("LocalEditor Design") is what install dialogs, Settings and the Dock or Start menu show.

**Ids.** An installed app is known by its `id`. The suite keeps `/`, which existing installs already have. The studios use their own paths. Changing an id later would orphan existing installs, so `tests/install.test.js` pins them.

**What each app opens.**

| | Suite | Design | PDF |
|---|---|---|---|
| `file_handlers` | images, `.leproject`, `.leworkflow` (as before) | images, `.leproject`, `.ledesign.json`, `.leworkflow` | `.pdf`, `.lepdfworkflow` |
| `share_target` | images and design files to `/studio/` (as before) | the same, with `&app=design` | PDFs and PDF workflows to `/pdf-studio/?share-target=1&app=pdf` |
| `shortcuts` | studio, collage, PDF studio, protect a PDF | new design, collage, remove a background | open a PDF, merge, protect, safe to send |
| `launch_handler` | `navigate-existing`, then `auto` | same | same |

Files opened with LocalEditor PDF reach the PDF studio through `PS.addFiles` (a small bridge in `le-pwa.js`). A `.lepdfworkflow` opens the Saved workflows job and imports the file through the job's own Import button. The worker parks shared PDFs exactly as it parks shared photos, then opens `/pdf-studio/?shared=<id>`.

**Icons and colours.** All three use the same icon set and the same neutral theme and background colours: editor chrome never carries a hue (docs/DESIGN.md). The home-screen names tell them apart. A small badge per app (a design or PDF glyph in a corner of the mark) is **not** made: `scripts/screenshots.js --icons-only` draws every icon, and it is not one of the files this change may edit. To add badges, add three lines to `brandIcons()` there: draw `icon.svg` with the `studio` or `pdf` shortcut glyph in a 160 px circle at the bottom right, write `assets/icons/icon-design-512.png` and `icon-pdf-512.png` (plus maskable versions), then point `appManifestJSON` at them.

## Choosing at install time

Every Install entry (the shell menu's "Install app", page buttons with `data-le-install`, the nudge's Install button) opens the chooser: **Everything** (recommended), **Design studio only**, **PDF studio only**. Each choice has one sentence, its approximate size on the device (the app's raw bytes from `packs.json`), and the name it gets on the home screen. On `/studio/…` the design studio is pre-selected; on `/pdf-studio/…`, the PDF studio; anywhere else, Everything. An app this browser already installed is shown as "Installed on this device" and cannot be picked.

The chooser changes nothing about how often we ask. The nudge has the same rules as before (after real use, backing off after "Not now", never in-app), and it never appears again once any LocalEditor app is installed. Install entries disappear inside an installed app and once the whole suite is installed.

### How a choice becomes an install

A page links one manifest, and the browser installs whatever the page links at that moment. Pages keep linking the suite manifest. Choosing a studio switches the link (`LEPwa.linkManifest(app)`, which also sets `apple-mobile-web-app-title`):

1. **Browsers with an install prompt (Chromium: Chrome, Edge, Samsung Internet, Opera).** Switch the link, wait up to 4 seconds for a fresh `beforeinstallprompt` for that manifest, and call `prompt()` from the same tap. Chromium needs a recent tap for `prompt()`; if the tap has expired, the sheet says "Ready. Tap Install once more to finish." After the prompt the page links the suite again, so the browser's own install icon goes back to offering everything. If no prompt arrives (already installed, or the browser declines), a studio chosen outside its pages opens its start page with `?install=<app>`; otherwise the sheet shows the browser-menu steps.
2. **Browsers without a prompt (Safari on iPhone, iPad and Mac, Firefox for Android).** The steps for this browser are shown under the choices, after the chosen manifest is linked. A studio chosen on another page shows "Open the design studio" (or the PDF studio) instead. That navigates to the app's start page with `?install=design`. That page links LocalEditor Design, removes the parameter from the address and opens the chooser with the choice kept and the steps shown. The person then uses Share → Add to Home Screen (or File → Add to Dock), which reads the linked manifest. The link stays switched after the sheet closes, because that is when the person adds it.
3. **Firefox on desktop** cannot install web apps. Install entries stay hidden, as before. If someone arrives with `?install=`, the sheet says so plainly and explains that the site still works offline in the tab.
4. **In-app browsers** (Instagram, Facebook, …) still get "Open in your browser".

### Which app is installed, and which window is which

- **Installed from this browser.** Recorded in `localStorage le-pwa` (`apps: { design: time }`) on `appinstalled` or an accepted prompt (the app that was prompted for), and on the first launch of an app whose install the browser did not report (Safari). If the browser later offers a prompt again for an app it had installed, that app counts as removed. The OS removes apps. We never claim more than we saw, and `getInstalledRelatedApps` is not used: it is for store apps.
- **This window.** Each start page carries `?app=design` or `?app=pdf`. In `display-mode: standalone` (or `navigator.standalone` on iOS), the window remembers it in `sessionStorage` (`le-pwa-window-app`) for its whole life. A window without the marker (opened from a link) counts as the most specific installed app whose pages include it, else the suite.

## Nested scopes in Chromium (tested, not assumed)

Tested on 12 November 2026 in Chrome for Testing 153 (Linux, new headless), with real installs through the DevTools `PWA` domain. `PWA.install` is what the install dialog does, and `PWA.launch` opens real app windows. Each app was set to open in its own window. To tell windows apart, the experiment gave one app `display: minimal-ui`. Scripts: `tests/install.test.js` (installability and ids). The window experiment is described below, so it can be repeated.

| From | Link | Result |
|---|---|---|
| Suite window (`/`) | `/studio/`, same window | Stays in the **suite window** (in its scope). It does not jump to the Design app. |
| Suite window | `/studio/`, new window (`target=_blank`) | Opens a **LocalEditor Design** window (the most specific installed scope wins). |
| Design window | `/pdf-studio/`, same window | Stays in the **Design window**, out of its scope. Chromium shows its out-of-scope bar with the address and a close button. `display-mode` is unchanged. |
| Design window | `/pdf-studio/` or `/`, new window | Opens the **PDF app** if installed, else a **suite window** if installed, else a **browser tab**. |
| PDF window | `/studio/`, new window | Opens the **Design app** if installed, else suite, else browser tab. |
| Browser tab | `/studio/`, same window | Stays in the tab. |
| Browser tab | `/studio/` or `/pdf-studio/`, new window | Opens the app that owns the page (Design, PDF, else suite). This is link capturing, which these installs had on by default. |
| Any, with link capturing **off** (`PWA.changeAppUserSettings`) | new window | Always a **browser tab**, even for pages inside the suite's scope. |
| Any app with `launch_handler: navigate-existing` | captured link or launch | **Navigates that app's existing window** instead of opening another. |

Installing a studio from a page outside its scope works in Chromium too. A fresh `beforeinstallprompt` fires for the Design manifest on `/`, no installability errors are reported, and `PWA.install` succeeds. The chooser therefore installs in place on Chromium and only travels to the studio when no prompt comes. Installing the Design app does not install the suite, and the reverse holds too. The two coexist, and each keeps its own file handlers.

**What we do with it.** Inside LocalEditor Design or LocalEditor PDF, a click on a link outside that app (the shell's menu, "Edit a PDF", a tool page) opens a **new window**: the suite or the other studio when installed, otherwise the browser. The studio window is never stranded on a page that does not belong to it. Offline, if that page is not kept on this device, a notice says so ("The PDF studio is not kept offline here … Storage") instead of opening an empty window. Links inside the app, and links in the suite, are left alone.

## Offline per app

`scripts/build.js` splits the Basic editor into four parts by following what each studio page really loads. That means `<script src>`, `<link href>`, `LE.modules.defer` sources, `url()`, then the string paths and bare vendor file names inside the code they load, all the way down. `packs.json` gets `parts` and `apps` (the build prints them). Figures from 12 November 2026:

| Part | Files | On the device (raw) | Download (transfer) | What |
|---|---|---|---|---|
| Shared app files (core) | 50 | 5.4 MB | 1.9 MB | shell, styles, install/downloads/support code, icons, the three manifests, home, offline page, plus what both studios load (engine, objects, fonts, assets, pdf.js, pdf-lib, fontkit, SheetJS, JSZip, QR) |
| Design studio | 82 | 2.4 MB | 0.7 MB | studio page, `le-studio*`, makers, collage, cut-out, agent, recipes, Expert (while it joins the first download) |
| PDF studio | 20 | 1.8 MB | 0.5 MB | PDF studio page, `le-pdf-*`, convert, mammoth, html2canvas, marked, DOMPurify |
| Tools and pages | 82 | 1.5 MB | 0.5 MB | tool pages, hubs, feature pages, licences, home images |

| App | Parts | On the device | Download |
|---|---|---|---|
| LocalEditor (or a plain browser visit) | all four | 11.1 MB | 3.6 MB |
| LocalEditor Design | core + design | 7.8 MB | 2.6 MB |
| LocalEditor PDF | core + pdf | 7.3 MB | 2.4 MB |

**Where the choice is stored: a cache entry, mirrored in localStorage.** The worker cannot read localStorage. It needs the choice when a new version installs, and a message only reaches a worker that is already running. So the choice lives in `le-packs-v1` at `./__packs/app` as `{ app, keep: ['design'] }`, next to the Expert marker that already works this way. That cache is in the worker's `KEEP` list, so it survives every update. "Erase everything" removes it, and the storage manager lists it under App files. `localStorage le-downloads-keep` mirrors it for instant reads in the UI. On every page load `LE.downloads` copies the cache back into the mirror, so "Reset all settings" cannot leave the two out of step. No marker means "everything", which is exactly the behaviour before this change.

**The worker.** `swMain` gets a fifth argument, `PARTS` (`{ parts: { core, design, pdf, tools }, bytes, full, limit }`). When a version installs, it reads the marker. Without one, it downloads `ASSETS` exactly as before, the suite list. With one, it downloads core plus the kept parts: whole when that is under 25 MB or Basic already downloads whole (today), otherwise only their critical files. The Expert files follow the design part. There is still one worker at the root, and the update safety is untouched: a new version waits and never activates over unsaved work (`le-apply-if-idle`, `le-skip-waiting`).

**When it changes.**
- Installing **the suite** keeps everything.
- Installing **a studio first** keeps that studio only. The other parts leave the current version's files at once (that is what "studio only" means), and later versions skip them.
- Installing **a second app** adds its part to what is kept. Design after PDF keeps both; the suite after a studio keeps everything.
- Settings → **Downloads for offline use → Kept offline** (in the storage manager and the downloads sheet) shows "Installed: Design studio only · about 7 MB on this device". It then lists one row per part with its size and real state (checked in the caches), plus **Keep offline** (downloads that part now: the row showed its size), **Remove** (two taps: "Remove the offline files of the PDF studio"), and **Keep everything offline**. "Download now → Basic editor" (or a pack containing it) also keeps everything from then on.
- A part that is not kept still works online. Its code is cached as it is used, as before for `/assets/`, and pages are now cached as they are visited too. Offline, a page of a part that is not here gets the offline page, which names the missing studio ("The PDF studio is not kept offline on this device…") and lists only links that are on the device.

API: `LE.downloads.parts()`, `apps()`, `keep()`, `setKeep(parts)`, `chooseApp(app)`, `addPart(id)`, `removePart(id)`, `keepEverything()`, `keepSummary()`. `LEPwa.apps`, `openChooser({ app })`, `installedApps()`, `currentApp()`, `pageApp()`, `linkManifest(app)`, `linkedApp()`.

## What CloudFront needs

- **Content type and caching for the new manifests.** `manifest-design.webmanifest` and `manifest-pdf.webmanifest` must go up as `application/manifest+json` with `no-cache`, like `manifest.webmanifest`. Done in `scripts/deploy.sh`: pass 6 now includes `"manifest-*.webmanifest"`, and the pre-flight checks that all three exist and are valid JSON. Run the next deploy with `--full` once, or at least make sure the two new files are uploaded by pass 6 (they are new, so `sync` uploads them).
- **Share target for LocalEditor PDF.** `infra/cloudfront/viewer-request.js` now answers a POST to `/pdf-studio/` the way it already answers `/studio/`: a 303 to `?shared=failed`, for the rare case where the share reaches CloudFront before the worker runs. Publish the updated function (docs/DEPLOY.md 4b). Without it, that rare case gets a 405, which is harmless.
- Nothing else: the same worker, the same headers policy, no new hosts.

## Tests

`node tests/run.js install`. It covers the three manifests (valid, generated, distinct stable ids, start URL inside scope, icons exist, short names fit, file types per app, deploy and precache). It checks that Chromium reads each manifest and fires a fresh prompt per link switch, with a real install of LocalEditor Design. It checks the chooser at 360 px and desktop in light and dark: three choices, sizes, plain words, 44 px targets, button contrast, no sideways scroll, pre-selection on the studios. It checks each choice fires the prompt with the right manifest linked. On Safari it checks the trip to the studio page, with the choice kept, the link and title switched and the address cleaned. It checks the Firefox wording; per-app precache lists (shell included, the other studio excluded, parts disjoint, suite unchanged); a Design-only install offline (studio works, PDF page polite, update follows the choice, choice survives the update, pages kept as used); the Settings rows (installed, add, remove, keep everything); and cross-links inside the Design app. `pwa` and `downloads` keep their guards, adjusted only where the Install entry now opens the chooser first.
